# ShedShare backend setup

The backend uses the existing MySQL 8 schema for relational data, Supabase Auth for signup verification and Google-linked accounts, Supabase Storage for item images/videos, and Paystack for verified rent payments. Supabase's service-role key and Paystack secret stay on the API server.

## Production deployment readiness

The relational application database is **MySQL 8**; Supabase Postgres is not used by this codebase. Supabase provides Auth and Storage. Deploy a reachable MySQL 8 database alongside the API, and deploy the frontend on the API origin or on a subdomain within the same site. The session cookie uses `SameSite=Lax`; a frontend on a different registrable domain will not send it on cross-site API fetches even when CORS allows that origin. For a separate frontend origin, set `API_BASE` and configure exact HTTPS `ALLOWED_ORIGINS` values.

Before deployment:

1. Set production environment variables on the hosting provider, not in a committed `.env`: `NODE_ENV=production`, `AUTH_MODE=supabase`, production MySQL credentials, a random `JWT_SECRET` of at least 32 characters, the production Supabase URL/anon/service-role keys, `SUPABASE_STORAGE_BUCKET`, the production HTTPS `EMAIL_VERIFICATION_REDIRECT_URL`, exact HTTPS `ALLOWED_ORIGINS`, and `PAYMENT_MODE=manual` (the default). Manual mode suspends online payment initialization and enables direct lister bank transfers with lister confirmation. Apply migrations `035_manual_installments.sql` and `036_manual_installment_cancellation_audit.sql` before enabling the manual booking flow.
2. Create/verify Supabase buckets: public `shedshare-media`, private `shedshare-rider-private`, private `shedshare-chat-private`, and private `shedshare-request-references-private` (or use the corresponding bucket environment overrides). Request-reference images must remain private; the API serves them only to their requester or an administrator. Configure Supabase email confirmation, SMTP, allowed redirect URLs, and the email template as described above.
3. Back up the production MySQL database, then apply migrations once with `npm run migrate`. Migration 035 adds listing installment preferences, per-booking installment snapshots and transfer audit records, and commission obligations. Migration 036 adds cancellation audit events for unpaid installments. Never run concurrent migration jobs. The local database being current does not apply these changes to production.
4. Before deploying the private request-image API, run `node scripts/migrate-request-reference-images.js` with the production environment to review the dry-run counts, then run it with `--apply` to move recognized existing public request images into the private bucket and remove their public copies. Investigate any unrecognized rows separately; the script leaves them unchanged. Keep a database and storage backup before applying.
5. Set `TRUST_PROXY_HOPS` to the exact number of trusted reverse proxies in front of Express. The proxy must forward the original HTTPS scheme safely; production redirects HTTP requests only to a matching HTTPS origin in `ALLOWED_ORIGINS` and rejects unmatched hosts.
6. Run `npm test` and `npm run preflight:production` with the deployment environment. Preflight checks configuration shape; it cannot verify hosted database connectivity, Supabase dashboard setup, DNS/TLS, bucket existence, or Paystack onboarding.
7. Start the API and check `GET /api/health`. It reports the payment mode without exposing secrets. Before live payments, set `PAYMENT_MODE=paystack`, provide a valid production `sk_live_` key, then run the Paystack sandbox booking and verify the 15% platform/85% owner split and platform-paid processing fee. Production rejects missing, invalid, or test keys in Paystack mode.
8. Confirm production frontend/API URLs, Google OAuth origins and callback, legal terms/privacy notices, backups, logs/alerts, and a support contact. Maps and external business search are optional; without their restricted Google keys those features remain unavailable. Email/push/SMS rental notifications are not implemented; users receive in-app notifications only.

### Manual bank transfers and installments

With `PAYMENT_MODE=manual`, listers configure their receiving bank and account in **Account settings** and opt into a deposit-and-balance plan per listing. The first installment is due when the agreed booking is created; the remaining amount is due 24 hours before the rental starts. If that deadline is too close, the agreement uses full payment. Amounts are stored in minor units and the remainder absorbs rounding so installments sum exactly to the accepted rental price. Paystack mode uses full checkout; it does not apply a manual installment schedule. Transfer details are snapshotted to each booking and shown only to its participants. A renter report is pending until the lister or an administrator confirms receipt; the confirmation records that money reached the lister, not ShedShare. The platform commission stays due until an administrator records actual receipt. Current manual installment support is for ordinary rental listings; event planner bundles and supplier offer acceptance do not use this installment flow yet.

For local account testing without Supabase email verification, set `AUTH_MODE=local` in `.env` and restart `npm start`. New test accounts are bcrypt-hashed and stored in the configured MySQL database, marked verified, and signed in immediately. Google sign-in is hidden while this mode is active. Supabase auth remains available by setting `AUTH_MODE=supabase` and restarting; local-only accounts do not gain Supabase identities, so use separate test accounts for each mode. Local auth is rejected when `NODE_ENV=production`.

## Local API

1. Install Node.js 18 or newer and MySQL 8.
2. Create a database and least-privilege application user. Copy `.env.example` to `.env` and enter real credentials. Generate a random `JWT_SECRET` with at least 32 characters.
3. In Supabase, create a project, copy its project URL, anon key, and **service role** key into `.env`, enable email confirmations, configure the SMTP provider and allowed redirect URL, and create a public Storage bucket named `shedshare-media` plus a private bucket named `shedshare-request-references-private` (or set `SUPABASE_STORAGE_BUCKET` and `REQUEST_PRIVATE_STORAGE_BUCKET`). Supabase Auth sends the confirmation link; Gmail can be used as the custom SMTP sender if Google Workspace/Gmail SMTP credentials and app-password policies are set up. A normal Gmail address/password is not sufficient for SMTP.
4. Configure `EMAIL_VERIFICATION_REDIRECT_URL` as the deployed ShedShare frontend URL. Add it to Supabase Auth's allowed redirect URLs and keep Supabase's confirmation template configured to return either a `token_hash` or a confirmed session access token in the URL hash; ShedShare verifies either form server-side before allowing login.
5. In Google Cloud Console, create a Web OAuth client. Add your local and deployed website origins to Authorized JavaScript origins. Set its client ID in server `.env` as `GOOGLE_CLIENT_ID`; the website reads this public ID from `/api/config`. Google sign-in also requires the Google Identity Services script to load in the browser.
6. Keep `PAYMENT_MODE=manual` while payments are suspended. When ready to activate Paystack, complete business verification and platform onboarding, set `PAYMENT_MODE=paystack`, and use the environment-appropriate server-only key (`sk_test_` for development, `sk_live_` for production). Authenticated owners then connect payout subaccounts through `POST /api/auth/paystack/subaccount`. Do not store card data. Register `https://<api-domain>/api/payments/paystack/webhook`; validate HTTPS callbacks, webhook delivery, account eligibility, and settlement splits before live use. Switching the mode does not migrate, duplicate, or charge existing bookings; existing bookings and their payment records stay unchanged.
7. Install packages with `npm install`, apply migrations with `npm run migrate`, then start with `npm start`. In local development, the API also serves the ShedShare website at `http://localhost:3000`, so one terminal runs both the frontend and backend.
8. Set `API_BASE` in `script.js` to the deployed API origin. In `manual` mode, Paystack initialization routes return 503 and rental checkout is unavailable. In `paystack` mode, API-backed checkouts use server initialization and webhook plus provider verification. When `API_BASE` is empty, the preview does not accept or mark rental payments as paid.
9. Set `ALLOWED_ORIGINS` to the exact frontend origin (no path) and `TRUST_PROXY_HOPS` to the number of trusted reverse proxies. Production requires a Paystack key only when `PAYMENT_MODE=paystack`.
10. After production is reachable, call `GET /api/health`; it reports MySQL connectivity plus whether required credential/configuration values are present, without revealing credentials. It does not prove that the Supabase buckets exist or that provider APIs are reachable. Run the Paystack sandbox flow and verify the account settlement split in the Paystack dashboard before switching to live keys.

## Phone notifications and app badge

Phone alerts use standards-based Web Push through the browser's push service; ShedShare does not need a paid notification provider. Generate one persistent VAPID key pair with `npm run setup:web-push`. Keep both generated values server-side in the local `.env` or hosting secret settings; never commit or expose the private key. Apply migrations with `npm run migrate`, deploy the service worker/API, and serve the installed PWA over HTTPS. Users must sign in, allow notifications on their device, then enable **Phone notifications** in Account & Settings. The browser/device may limit app-icon badge appearance and background delivery.

Production deployment requires the same `WEB_PUSH_PUBLIC_KEY` and `WEB_PUSH_PRIVATE_KEY` in the API host's environment. The local `.env` keys do not configure the deployed service. The project currently records `https://shed-share.netlify.app` as an allowed frontend origin but does not record the matching public API origin/host; configure the app to call the deployed API and add the frontend/API origins to the API host before expecting phone alerts from the published site. No contact email or paid API key is needed.

The in-app badge includes unread notifications and, for administrators, all pending rider applications until each application is approved or rejected. Push alerts require the user to opt in on each device. The app icon badge is best-effort because operating systems and browsers decide how to display it.

Rider delivery checkout uses a separate Paystack transaction after a rider accepts and quotes a fee. Apply migrations `023_rider_delivery_payments.sql` and `024_configurable_commission_rates.sql` before deploying rider checkout and commission settings. Admins can change rental and rider commissions from the dashboard (0–100%, in 0.01% increments). Rates are snapshotted into a rental summary or rider quote and remain fixed for that payment; changing dashboard rates applies to new summaries and quotes. Paystack routes each configured share to ShedShare as `transaction_charge` and pays the remainder to the connected owner or rider subaccount. The webhook checks the stored amounts and rate before confirming payment.

Migration 001 defines the core schema for fresh installs; migrations 002–015 add authentication/payment upgrades, request and dispatch tables, administrator safety controls, Google Maps locations, trust workflows, and shared checkout rate limits. Review and back up production data before applying schema migrations. Checkout initialization and offer acceptance share a database-backed limit of 10 attempts per user per 15-minute window; migration 015 must be applied before deploying that code.

## Google Maps Platform

ShedShare uses Geoapify map tiles with Leaflet for interactive maps, address suggestions, search, and reverse geocoding. Normalized results are cached in MySQL (`geocode_cache`). Browser geolocation supplies device coordinates when a member chooses their location; Geoapify turns coordinates into a readable address. Search radius and listing distance use ShedShare's Haversine calculation; browsing makes no Routes calls.

In Geoapify MyProjects, create separate browser and server keys:

- `GEOAPIFY_MAPS_BROWSER_KEY`: used to load Geoapify tiles in Leaflet. Restrict it to exact local/deployed website origins.
- `GEOAPIFY_API_KEY`: server-side key for autocomplete, address verification, search, and reverse lookup. Store only in the server `.env`/secret manager and restrict it to the API services the server uses.

Keep the browser key out of frontend source files; the server provides it through `/api/config`. Keep the server geocoding key private. Geoapify's free map styles require Geoapify, OpenStreetMap, and (for most styles) OpenMapTiles attribution on the map.

Set both Geoapify keys in `.env`, restart the API, and apply `npm run migrate` (migration 005). Missing keys leave listing browse and text search available and show a clear map diagnostic.

In Google Cloud Console → APIs & Services → Quotas, set a hard daily request quota for each enabled Maps/Places/Geocoding API to the business-approved ceiling. Confirm the quota is an enforceable daily cap and test what happens when it is reached. Budget alerts only notify; they do not stop billing. Review quotas and usage regularly, and use a billing account limit or disable APIs for an emergency stop.

Places Autocomplete is restricted to Nigeria. Listing submission requires city and state, verifies the selected Place ID with server geocoding, caches the result, and stores exact pickup address privately. Public APIs expose only area/city/state plus an independently jittered approximate point (~300 m). Rental responses disclose the exact address only for confirmed/active/completed rentals to the authenticated renter/owner. New listing request and availability alerts use in-app notifications; outbound email delivery is not added here.

## ShedShare Request and Dispatch API

Migration 003 adds the follow-on workflow tables. Customers can create requests with `POST /api/requests`, list their requests with `GET /api/requests?mine=1`, and read a request with its offers. Admin detail responses include category/location/date-matched supplier candidates; `POST /api/requests/:id/notify-suppliers` accepts selected `candidateOwnerIds`. Request reference images use `POST /api/requests/reference-image` with a multipart `image` field (JPEG, PNG, or WebP, up to 5 MiB). These images are stored in the private `REQUEST_PRIVATE_STORAGE_BUCKET` and fetched through an authenticated API route. The request-expiry window defaults to 14 days and administrators can update it with `PATCH /api/admin/settings/request-expiry`.

Suppliers submit offers through `POST /api/offers`. The customer accepts or declines through `/api/offers/:id/accept` or `/decline`; offer acceptance that initializes checkout is available only in `PAYMENT_MODE=paystack`. Only the signed Paystack webhook plus provider verification confirms that rental payment. Messages use `/api/messages`; notifications use `GET /api/notifications` and `PATCH /api/notifications/:id/read`.

Apply migration 009 with `npm run migrate`. Rider applications use `POST /api/rider/apply`; applicant images are uploaded through `POST /api/rider/application-documents/profile` and `/id` to a private storage bucket. Only administrators can retrieve bytes with `GET /api/rider/applications/:id/document/:kind`; the application API stores private object paths, never public URLs. Create a private Supabase Storage bucket named `shedshare-rider-private` (or set `RIDER_PRIVATE_STORAGE_BUCKET`) and leave public access disabled. Applicants must connect their existing Paystack subaccount through `POST /api/auth/paystack/subaccount` before applying. Admins review with `GET /api/rider/applications` and `PATCH /api/rider/applications/:id/review` (`approved`, `rejected` with reason, or `suspended`). Status changes create in-app notifications. Approval is one-time; suspension forces the rider offline and revokes uncollected assignments. If a rider is suspended after pickup, the delivery is moved to exception for support follow-up; it is not silently re-offered with the item already in transit.

Approved riders see offers in the Rider dashboard. Offer expiry is `RIDER_JOB_OFFER_MINUTES` (2 minutes); an accept operation claims the delivery under a database lock so only one rider can win. Offer cards contain item photo, distance, fee, and approximate areas; exact addresses are shown after acceptance. Riders can decline or cancel. Cancellations are recorded; `RIDER_CANCEL_WARNING_THRESHOLD` (3) sends a rider warning and `RIDER_CANCEL_REVIEW_THRESHOLD` (5) alerts admins. Riders progress delivery through collection and submit the renter's 4-digit hand-over code; possession of that renter-provided code records the renter's hand-over confirmation and completes the delivery. Renters can rate a completed rider delivery 1–5. `RIDER_LOW_RATING_THRESHOLD` (3.5) and `RIDER_LOW_RATING_MINIMUM_COUNT` (3) flag low averages for admin review. The rider dashboard lists completed delivery amounts from recorded delivery fees.

Notifications use the existing persistent in-app notification system. No email or push provider is configured in this repository, so status changes and hand-over codes appear in ShedShare notifications. No map tracking work is added as part of this rider application/dashboard update.

**Payout conflict requiring product confirmation:** the current payment model keeps rider delivery fees as a direct renter-to-rider payment after delivery, outside Paystack. The rider dashboard displays completed delivery fee amounts; this change does not route rider fees through Paystack or change split logic. Rider subaccount setup reuses the existing account verification flow. Confirm separately if rider fees should move to a platform-controlled Paystack split, since that changes the payment flow and the existing direct-payment rule.

Administrators can view accounts with listings at `GET /api/admin/listers`, pause or resume a lister's listings, pause new checkout initialization, review contact-sharing attempts, and place confirmed or active rentals on safety hold. A safety hold blocks further rental lifecycle actions; it does not reverse or recall funds already settled by Paystack. Pausing checkouts prevents new payment initialization; a checkout already open with Paystack may still complete. Common phone and email patterns are hidden from message text before it is stored, and flagged attempts are visible to administrators without retaining the original contact details. Riders can submit GPS updates during an active assigned delivery; the map only displays the latest location a rider has shared.

## ShedShare Live delivery

Migration 006 adds explicit owner/rider delivery methods, short-lived rider GPS, private rider-online positions, delivery offers, and one latest tracking point per delivery. Apply it with `npm run migrate`; it removes older duplicate location-history rows before adding a unique delivery key. Pickup remains the default. Owners can offer existing owner delivery or ShedShare rider delivery when their listing has delivery enabled.

The renter pays the rental subtotal through the existing Paystack owner split. Rider delivery fees are a separate transaction directly between renter and rider after delivery; the rider fee is not included in the ShedShare Paystack checkout or verified rental total. Agree the amount before the rider accepts. Owner delivery fees and deposits also remain direct arrangements under the current payment model.

After verified rental payment, rider jobs are offered to approved Online riders whose fresh private GPS is within `RIDER_SEARCH_RADIUS_KM` (default 10) of the item's stored pickup coordinate. The first rider acceptance claims the job in a database transaction. If there is no acceptance before `RIDER_OFFER_TIMEOUT_MINUTES` (default 10), the next rider-offer or tracking request marks the job `fallback_available` and notifies renter and owner to arrange Pickup or Owner delivers. Cancellation after acceptance clears the rider/location and offers the job again. Existing delivery confirmation remains unchanged: both rider and recipient confirmation complete the delivery. Confirmed/completed rental and payment records are not changed if map or GPS services fail.

All delivery controls live in `delivery-config.js` and can be overridden in `.env`: `RIDER_SEARCH_RADIUS_KM` (10), `RIDER_OFFER_TIMEOUT_MINUTES` (10), `DELIVERY_LOCATION_INTERVAL_SECONDS` (15), `DELIVERY_LOCATION_MIN_MOVEMENT_METERS` (20), `DELIVERY_LOCATION_STALE_SECONDS` (90), `DELIVERY_MAX_TRACKING_HOURS` (6), `DELIVERY_MAX_SPEED_MPS` (55), and `DELIVERY_LOCATION_RATE_LIMIT_PER_MINUTE` (6). The browser tracking refresh is 10 seconds. Bounds and safe fallback values are enforced in the config module. Tracking requests require backend authentication and one of the renter, owner, assigned rider, or admin identities. The rider's online job-matching location is never returned by any API. GPS tracking uses HTTPS and browser permission; Android Chrome or desktop may pause GPS when backgrounded or locked. The rider console requests Screen Wake Lock where the browser supports it and tells riders to keep the screen open.

Live tracking polls every 10 seconds while its view is open, keeps no location history, hides points older than the stale threshold, and deletes the latest point when tracking ends. Maps failures and missing GPS have separate messages. The renter can see the rider's latest shared position while tracking is active; rider GPS updates are sent about every 15 seconds while the rider dashboard remains open.

Geoapify map tiles, geocoding, reverse geocoding, and autocomplete use the two restricted keys described above. Review usage and quotas in Geoapify MyProjects. The browser key is returned by `/api/config` only when the admin map control is enabled; never put the server key in frontend code.

## Optional external business search (disabled by default)

Migration 007 adds a 24-hour external-search cache containing only the normalized query hash, Google place IDs, and expiry. Click leads contain place ID, searched item, city/state, user ID (when known), action, and timestamp. Search result details and 15-minute opaque redirect codes stay in server memory; a process restart can cause a fresh Google query for a cached query because business details are not persisted. The feature requires a signed-in user, an explicit search-button tap, item/city/state, and at least `MIN_LISTINGS_FOR_EXTERNAL` active ShedShare listings in that city/state (100 by default). Each user gets `EXTERNAL_SEARCH_MAX_PER_USER_PER_DAY` searches (5 by default). `EXTERNAL_SEARCH_BIAS_RADIUS_METERS` defaults to 5,000. The server uses the average stored coordinates of active listings in that city/state as the Text Search location bias. If none exist, it asks the user to choose a location rather than issue an unbiased request. Config defaults and bounds are centralized in `external-search-config.js`.

To enable deliberately, set `EXTERNAL_SEARCH_ENABLED=true` and `GOOGLE_MAPS_PLACES_SERVER_KEY` in the server environment. Create a separate server-only key restricted to Places API (New); do not reuse the Geocoding key if that key is restricted to Geocoding. The new key is never returned by `/api/config` or sent to the browser. When the feature flag is false (the default), the endpoint exits before any Places request. In Google Cloud Console → APIs & Services → Quotas, set an enforceable hard daily quota for Places API. Budget alerts alone do not stop billing. Search results include the availability disclaimer and Google attribution, use Google Maps for directions, and never claim stock, price, or availability. Call, WhatsApp, and Directions clicks go through short-lived opaque redirects and create admin-visible lead counts per business/action.

For local development, use a strong `JWT_SECRET` even outside production and create the first administrator with the local setup command below. In production, promote only an account that completed the verified signup flow. The public frontend's demo admin email has no authority in API mode.

## In-app chat

Apply migration 008 with `npm run migrate`. Existing item messages are copied into participant-based conversations; the legacy table remains intact. Renter-initiated listing chats attach to the latest applicable rental when one exists, while a lister can open a thread only for an existing rental. Rider acceptance creates renter-rider and owner-rider chats in the same database transaction as the assignment. Delivery end closes both rider chats; rental completion locks its item chat after `CHAT_COMPLETION_LOCK_DAYS`.

Create a **private** Supabase Storage bucket named `shedshare-chat-private` (or set `CHAT_PRIVATE_STORAGE_BUCKET`). Keep bucket access private and let only the API service role upload/download. Chat accepts signature-checked JPEG, PNG, and WebP images up to `CHAT_MAX_IMAGE_BYTES` (5 MiB by default); endpoints require a participant authorization check before returning file bytes. Do not make this bucket public.

Chat settings are centralized in `chat-config.js` and can be set in the server environment: `CHAT_MESSAGES_PER_MINUTE` (30), `CHAT_RETENTION_MONTHS` (12), `CHAT_COMPLETION_LOCK_DAYS` (7), `CHAT_MAX_IMAGE_BYTES` (5 MiB), `CHAT_STREAM_POLL_MS` (5000), and `CHAT_NOTIFICATION_BATCH_MINUTES` (5). A daily cleanup removes message rows older than the retention period. Conversation metadata, reports, blocks, and audited admin reads remain available for moderation. Admin dispute reads use `GET /api/admin/conversations/:id`; each read is recorded in `chat_admin_access`.

The inbox uses authenticated Server-Sent Events and falls back to authenticated polling. Message bodies are rendered as text in the browser and are never written to server logs. Contact details are redacted until the rental is confirmed/paid; after that, the renter/owner conversation can include them. Rider phone numbers are not included in conversation payloads. Report and block actions are available in every chat.

The existing backend has a persistent in-app `notifications` table but no general email or Web Push sender. New-message alerts are therefore batched into in-app notifications and shown on the user's next visit; add an email/push provider separately if offline delivery must happen outside ShedShare. Chat notification failures do not affect message, payment, rental, or delivery writes.

## Rental trust workflows (migrations 010–014)

Apply migrations `010_rental_trust_workflows.sql` through `014_remove_unplanned_refund_workflow.sql` using `npm run migrate`. The application has no refund route; migration 014 removes the temporary refunded rental/payment states and restores the planned split-checkout lifecycle. On this development database, the unused `rental_refund_requests` table is empty and inert because the app database user lacks permission to drop tables; a database administrator can remove it. New installs do not create that table. The remaining migrations add item cancellation/condition details, inquiry-only rental summaries, versioned mutual acceptance, inspection appointments, configurable checkout reservations, payment attempts and an accounting ledger, handover/return confirmations, extensions, disputes, notification preferences, trust roles, and admin audit logs. Inquiry summaries do not reserve dates or trigger a payment. A checkout reservation is created only after both parties accept the same terms. Only successful server-side payment verification confirms a booking.

The platform commission defaults to 15% for rentals and 5% for rider delivery; administrators can change either rate from the dashboard. `CHECKOUT_RESERVATION_MINUTES` defaults to 30 and administrators can adjust that reservation window. Deposits remain informational and are excluded from checkout. The `/terms` and `/privacy` text routes and chat UI disclose restricted staff message review and off-platform payment limitations. Before production, have counsel incorporate this disclosure into the full Terms of Service and Privacy Policy documents for the applicable jurisdictions.

Trust roles default to `none`; promote only explicitly authorized staff through `PATCH /api/admin/users/:id/trust-role` as a super admin. Every privileged chat read requires a reason and category, is read-only, and is audited. Chat report listing is also restricted to trust-and-safety roles. Existing ordinary admin accounts do not gain access by default.

Renters pay the rental charge through Paystack checkout. The owner receives the remainder after the configured rental commission through their linked Paystack subaccount. Paystack's processing fee is borne by the platform account, reducing the platform's share; it does not reduce the owner's allocation. Owner delivery fees and any informational deposit remain direct arrangements between the parties and are outside this split. Rider delivery is paid separately after the rider quotes; the configured rider commission goes to the platform and the remainder to the rider subaccount.

The checkout and return reminder scheduler is an idempotent in-process timer. For multiple API instances or guaranteed delivery across restarts, run a single scheduled worker or deploy a durable queue before relying on reminder timing. Email, browser push, and SMS are not active senders in this repository; `EMAIL_PROVIDER_URL`, `EMAIL_PROVIDER_API_KEY`, and Web Push keys are documented placeholders only. In-app events remain the only configured notification channel until a real provider adapter is implemented and configured.

For a local development database, `npm run setup:admin` interactively creates a verified admin account or updates an existing account's name, password, and admin flag. Password input is hidden, and the password is stored only as a bcrypt hash in MySQL. This helper refuses to run when `NODE_ENV=production` and requires the migrations to have created the `users` table first. Production accounts must use the normal verified signup flow and be promoted through the production database console.

## Payment boundaries

The API creates rentals as `pending_payment`. Paystack redirects the renter to its hosted checkout to select a supported payment method. Only a valid, signed Paystack `charge.success` webhook plus a successful server-side Verify Transaction response with matching reference, amount, and currency changes a rental to `confirmed`. Each owner subaccount uses a 0% main-account percentage by default; checkout overrides it with the flat `transaction_charge` computed from the commission rate stored in the rental summary and explicitly sets the platform account as the fee bearer. Paystack settles the platform share into the platform's Paystack balance and the remainder to the owner's linked bank via their subaccount. Neither full bank account number is displayed to renters. The deposit and delivery fee are excluded from the platform transaction and remain direct owner/renter arrangements.

## Media

The authenticated endpoints `PUT /api/items/:id/image` and `PUT /api/items/:id/video` accept `multipart/form-data` fields `image` and `video`. Images are signature-checked JPEG/PNG/WebP up to 8 MiB. Videos are signature-checked MP4/WebM/Ogg, up to 20 MiB and 60 seconds (requires `ffprobe-static`). The storage bucket currently returns public URLs for public marketplace listings.

## Existing-account note

Migration 002 adds `email_verified` as false by default. Existing users need an explicit email verification or administrator-reviewed backfill before they can log in; do not mark all legacy emails verified automatically. Set an administrator's `is_admin` field directly in the database.

## Security limits

No application can promise that hackers cannot break in. This project adds password hashing, one-hour JWT sessions in `HttpOnly`, `SameSite=Lax` cookies (`Secure` in production), double-submit CSRF tokens plus Origin/Referer validation on state-changing API requests, server-side role checks, exact CORS origin allowlisting, rate limits, security headers, parameterized SQL, upload size/signature checks, and signed payment webhooks. The frontend keeps only the user profile in memory; it does not read or write session tokens in browser storage. Helmet's Content Security Policy is currently report-only; review `/csp-report` logs while exercising Google sign-in, Maps, Supabase Storage, and Paystack checkout, then change `reportOnly: true` to `reportOnly: false` in `server.js` to enforce it. Production also requires correctly configured HTTPS proxy trust, protected provider secrets, a least-privilege database user, provider dashboard security, backups, monitoring, dependency updates, and a security review before real customer payments.
